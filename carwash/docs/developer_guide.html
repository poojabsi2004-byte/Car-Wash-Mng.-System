1. Module Architecture

The system is a chain of six installable Odoo apps, each depending on the previous. Every module is Community-edition only — no Enterprise modules appear anywhere in the dependency graph.

carwash_dashboard / carwash_website

Neither module adds new persistent business models. carwash.dashboard is a transient, non-stored model that exists only to expose one server method (get_dashboard_data()) to an OWL client action — there is nothing to query it directly for. carwash_website adds no models at all; it is controllers + security + templates over the existing carwash.appointment / carwash.vehicle models.

Cross-Module Extension Pattern

Later modules extend carwash.appointment via _inherit rather than new models — e.g. carwash_jobcard adds jobcard_ids/inspection_count and overrides action_ready() to gate on job-card completion; carwash_multibranch adds no fields at all, only ir.rule records. This keeps the base model's own file the single source of truth for the core fields and state machine.

R=read, W=write, C=create, U=unlink. * Washer/QC job-card access is further narrowed by an ir.rule ("washer sees only their own assigned job cards") — see below. Owner inherits Manager's full grant.

Real bug found and fixed this round: in Odoo 19, a groups="..." attribute inside a view's <button>/<page> arch is resolved at runtime against fully-qualified module.xml_id strings — unlike <menuitem groups="...">, which resolves bare names relative to the current module via the standard ref() mechanism. A bare groups="group_carwash_user" inside a form/kanban arch silently resolves to no group at all, which hides the element from every user, including the superuser (view-level group filtering is not bypassed by env.su). Always fully-qualify arch-embedded groups=, e.g. groups="carwash_base.group_carwash_user", even when the group lives in the same module as the view.

Record Rules (ir.rule)

Combination gotcha: Odoo ANDs together rules that have no groups field ("global" rules) with everything else, but ORs together rules that share a group. This system deliberately writes branch-isolation and ownership rules as global rules with a self-exempting domain (e.g. ... if not user.has_group('...group_carwash_owner') else []) rather than as group-specific rules — a group-specific "Owner sees everything" rule would OR with a washer's "only assigned job cards" rule instead of narrowing it, defeating the restriction entirely for any user in both groups.

4. State Machines

carwash.appointment.state

draft → confirmed → arrived → in_service → ready → done \→ cancelled confirmed \→ no_show
  • action_confirm() — requires at least one service line.
  • action_arrive() — stamps arrived_at (drives the "waiting time" KPI).
  • action_start_service() — requires a free bay; sets the bay to occupied; stamps service_started_at. carwash_jobcard also auto-creates a carwash.jobcard here.
  • action_ready() — frees the bay. carwash_jobcard overrides this to block until every open job card on the appointment has reached done/cancel (QC-gated).
  • action_done() — creates stock consumption moves and a confirmed Sales Order (both idempotent — skipped if already present).

Bay time-window guard: _check_bay_time_conflict (a @api.constrains) rejects any confirmed/arrived/in_service appointment whose [start, start+duration) window overlaps another appointment on the same bay in one of those three states. This supersedes an earlier, narrower version of the constraint that only checked in_service — the physical bay.state != 'free' guard in action_start_service() is unrelated and still applies on top of it (one guards the paper reservation, the other the physical bay).

carwash.jobcard.stages

draft → in_progress → qc → done ^ \→ in_progress (QC Fail / rework loop) draft/in_progress → cancel
  • action_start() — requires assigned_employee_ids; auto-creates a project.task on first start (idempotent).
  • action_submit_qc() — blocked while any checklist line is unchecked.
  • action_qc_pass() — stamps qc_inspector_id/end_time; auto-creates one account.analytic.line timesheet entry (end_time − start_time, attributed to the first assigned employee).
  • action_qc_fail() — sends the card back to in_progress and resets every checklist line to unchecked.

carwash.membership.state

active → expired active → cancelled

_bill_cycle() (called from a cron and from action_renew_now()) creates+confirms a Sales Order for the plan's billing product, advances next_billing_date by one period, and resets washes_used. Each covered wash increments washes_used via the appointment-done hook.

5. Booking & Slot-Availability Design

Business Hours

Reused wholesale from resource.calendar (via res.company.resource_calendar_id, brought in by the resource/hr dependency chain) — zero new fields or models. Each branch's hours are managed through the standard Employees → Working Schedules screen.

_get_available_slots(company, date, service)

An @api.model method on carwash.appointment that walks each resource.calendar.attendance window for the requested weekday in half-hour increments, and for each candidate slot counts how many of the branch's active bays are not already covered by an overlapping confirmed/arrived/in_service appointment. Returns [{start, bay_count, bay_ids}, ...] — one entry per slot that has at least one free bay. This is the same overlap logic as the model constraint, so a slot the method offers can never fail the constraint moments later under normal (non-concurrent) use.

Concurrency: Row Locking

Two customers can request the same slot in the same instant. A Python-level @api.constrains check alone is not enough under PostgreSQL's default READ COMMITTED isolation — both transactions can pass the pre-check before either commits.

The booking controller's _lock_and_pick_bay(company, start, end) issues SELECT id FROM carwash_bay WHERE id IN (...) FOR UPDATE against the branch's bay rows before re-reading existing appointments and picking a free bay. A second concurrent request blocks on that lock until the first request's transaction commits, then re-reads and correctly sees the first booking — so it picks a different bay, or reports the slot full, instead of double-booking. This is plain PostgreSQL row locking; no new infrastructure.

Controller Flow (no JavaScript)

The whole booking flow is server-rendered, plain HTML forms — GET → GET → POST → GET — deliberately avoiding a JS/ajax layer, since the environment this was built in has no way to browser-test client-side behavior. Every route is auth='user', so an anonymous visitor is auto-redirected to /web/login — this alone satisfies "portal login required to book."

7. Installation & Operations

Install Order

Standard Odoo dependency resolution handles this automatically — installing carwash_website (the leaf module) pulls in all five others. For a minimal single-branch, no-online-booking deployment, install only carwash_base + carwash_jobcard (+ carwash_membership if recurring plans are needed).

Demo Data

Every module ships realistic demo data (customers, vehicles, bays, a full day's queue including one intentionally in-progress appointment, a second branch, an Owner and a Branch Manager account) so a fresh install is immediately explorable without manual setup.

Multi-Company Note for Developers

env.companies (active/switcher-selected companies) and user.company_id (the user's fixed home company) are not the same thing and are easy to conflate. Dashboard and booking scoping consistently use env.companies so behavior follows the company switcher, not just the user's default branch.

Regression Testing

There is no formal Odoo tests/ package; verification throughout development used ad-hoc odoo-bin shell scripts exercising the full workflow per module plus targeted negative-path and cross-role access checks, re-run after every change against a clean reinstall.
